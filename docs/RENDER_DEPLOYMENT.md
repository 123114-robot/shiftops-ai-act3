# ShiftOps AI Render Demo Deployment

Date: 2026-10-16 (Australia/Sydney)

Status: deployment configuration prepared and locally verified. No Render resource has been created and no public deployment is claimed.

## Topology

The root `render.yaml` defines the smallest public demo topology:

- `shiftops-ai-web`: React/Vite Static Site.
- `shiftops-ai-api`: Express Node Web Service.
- `shiftops-ai-db`: PostgreSQL database in the same Singapore region as the API.

The API remains in `AI_MODE=deterministic`. This deployment does not establish live AMD inference evidence.

## Render settings

Use the repository root for both services. Leave **Root Directory blank**.

| Resource | Build command | Start / publish setting |
| --- | --- | --- |
| Static Site | `npm ci && npm run build -w frontend` | Publish directory: `frontend/dist` |
| Web Service | `npm ci && npm run db:generate && npm run build -w backend` | `npm run start -w backend` |
| Web Service pre-deploy | `npm run db:deploy -w backend` | Applies committed Prisma migrations only |
| Web Service first-deploy hook | `npm run db:seed:demo -w backend` | Additive, guarded synthetic seed |

Health check: `/api/health`

SPA rewrite: `/*` → `/index.html`

## Environment variables

The Blueprint manages these without committing secret values:

### API Web Service

- `DATABASE_URL`: injected from `shiftops-ai-db` private connection string.
- `JWT_SECRET`: generated by Render.
- `FRONTEND_URL`: set to the final Static Site origin, for example `https://shiftops-ai-web.onrender.com` with no trailing slash.
- `DEMO_SEED_ENABLED=true`: permits the guarded synthetic first-deploy seed.
- `DEMO_PASSWORD`: enter a unique 12+ character Demo-only password in Render; do not commit or send it in chat.
- `AI_MODE=deterministic`.
- `AI_PROVIDER=amd-token-factory`; no AMD key is configured or required while deterministic mode is active.
- `SHIFTOPS_MAX_WEEKLY_MINUTES=2400`.
- `SHIFTOPS_REQUIRE_ROLE_MATCH=true`.
- `PORT`: do not set manually; Render supplies it.

### Static Site

- `VITE_API_URL`: set to the final API URL with `/api`, for example `https://shiftops-ai-api.onrender.com/api`.

Never put `JWT_SECRET`, `DATABASE_URL`, AMD credentials or authorization headers in Git, screenshots, build logs or the frontend environment.

## Database safety

`backend/prisma/migrations/20261016000000_initial/migration.sql` is an initial baseline for a **new empty Render demo database**. The pre-deploy command uses `prisma migrate deploy`; it never calls `prisma db push`, resets the database or runs a development seed.

Do not point this baseline at an existing populated ShiftFlow database. For an existing database, stop and perform a schema diff and reviewed migration-baseline reconciliation first.

The demo seed:

- refuses to run unless `DEMO_SEED_ENABLED=true`;
- uses upserts and stable markers;
- creates only fictional users, availability, one demo shift and one demo leave request;
- never deletes, truncates or overwrites unrelated rows;
- can be rerun without duplicating the stable incident-demo shift.

Public synthetic Manager login:

- Email: `manager@shiftflow.local`
- Password: the owner-selected `DEMO_PASSWORD` stored only in Render.

This credential is intentionally public and must never be reused for real accounts or real data.

## Public demo acceptance flow

1. Open the Static Site and sign in with the synthetic Manager account.
2. Confirm Dashboard loads backend-derived values.
3. Open **Shifts** and confirm the synthetic Chef shift exists.
4. Open **ShiftOps Copilot**.
5. Enter Shift ID `demo-shift-incident` and an incident reason such as `Assigned employee unavailable`.
6. Select **Create incident and evaluate**.
7. Confirm Casey Lee is an eligible Chef candidate and role-mismatched employees remain blocked.
8. Create the Casey proposal and confirm the explanation source is deterministic.
9. Approve the pending proposal.
10. Apply the approved proposal.
11. Confirm the proposal reaches `APPLIED`, the shift assignment changes and audit history displays the incident/proposal/approval/apply events.

Do not describe this flow as live AMD inference. The first public demo proves the deployed deterministic, human-approved workflow only.

## Rollback

- Application rollback: use Render rollback/redeploy for the previously recorded commit.
- Database: migrations are additive and no rollback SQL is automated. Do not reset the database. For the disposable Demo environment, restore from a verified backup on a paid plan or recreate a fresh demo database after owner approval.
- Disable public access by suspending the Static Site and Web Service; do not delete the database without separate owner approval.
